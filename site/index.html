Getting started

Five minutes, then it works while you don't.

  1. 1

    Install it

    One Homebrew command. macOS 14+ on Apple Silicon — no account, nothing to sign up for.

  2. 2

    Connect your inbox

    Google doesn't let apps use your normal password, so you create a one-off app password instead: a 16-character code that unlocks mail and nothing else. Paste it into Sources with your Gmail address — EasyApply encrypts it with the macOS keychain and only ever reads.

    Where to get it: Google Account → Security → App passwords ↗. You'll need 2-Step Verification switched on first. Revoke it there any time and EasyApply simply stops reading — your account is untouched.

  3. 3

    Choose your model

    In Settings, pick a model and download it once — roughly 5 GB, kept on your disk. It runs on your own silicon: no API key, no token bill, no cloud. Switch it off and the RAM comes straight back.

  4. 4

    Press Start

    The activity panel opens and the agent starts working through the mail it has not read yet. Pause or stop it at any point.

  5. 5

    Let it read

    It judges every email, extracts the real postings, dedupes them against the six APIs, and drops them into your feed as it goes.

After that it stays out of the way: new mail is scanned on a schedule, and jobs land in the feed on their own. Turn the model off any time and the six APIs keep running without it.

Two lanes, one feed. The agent lane classifies your inbox with a local model of your choosing; the API lane pulls six boards inside their published rate limits. Both converge on the same dedupe and the same local database — and the UI only ever reads.

The agent

The AI runs on your machine. Not in someone else's cloud.

The best roles never reach an API — they land in your inbox as alert emails. So EasyApply points an agent at them: it reads each message, decides for itself whether that message holds real job postings, extracts the roles, and discards everything it can't stand behind. It runs on the local LLM you choose, through llama.cpp, on your own silicon. No API key. No token bill. No email ever uploaded. Turn it off and the RAM comes straight back.

01

Read the inbox

IMAP over TLS with an app password, encrypted at rest by the OS keychain. Only mail newer than the last scan.

02

Strip to text

Markup and tracking noise removed — but the anchors are kept, because the apply link is the one thing that must survive.

03

Extract

Each email gets a fresh 8k-token context, so one message can never bleed into the next. The model returns JSON.

04

Harness the output

Validated, then anchored on a real link: no title, company, or apply URL and the row is dropped. Hallucinations don't reach the feed.

05

Merge

The board is inferred from the apply link, deduped against all six APIs, and upserted per email — rows appear while the scan is still running.

The run is fully observable: a live funnel of scanned, accepted, and rejected emails, every prompt and response the model saw, transport controls to pause or stop mid-scan, and — for each email — the jobs it actually produced, linked to the original posting so you can check the model's judgement instead of trusting it.

Why it exists

Job hunting means six tabs, six logins, and the same posting three times.

Arbeitsagentur for Munich, four remote boards, Adzuna for the rest — each with its own search, its own noise, and the same role reposted under three names. And the best roles never reach an API at all: they land in your inbox as alert emails. EasyApply pulls every source with a real API into one deduplicated, newest-first feed on your Mac — then reads the alert emails too, with a model that never leaves the machine.

An agent reads your job alerts

LinkedIn and StepStone alerts hold inventory no API exposes. An agentic classifier reads each email, judges whether it holds real postings, extracts them, and merges them into the same feed — on the local model you pick, so your mail never leaves the Mac.

Every decision is inspectable

A live panel shows each email the agent scanned, the prompt and reasoning behind its verdict, and the jobs it kept — linked to the original posting. Pause or stop it mid-run. An agent you can audit, not a black box.

How it works

Honest plumbing

  1. 1.Sync — the main process fetches each source on an interval, one at a time, inside its published rate limits.
  2. 2.Normalize + dedupe — six response shapes become one job model, and the same role from two boards collapses into one row.
  3. 3.Local PGlite — everything lands in a Postgres-in-a-file on your disk. Nothing leaves the machine except the API requests themselves.
  4. 4.Read the inbox — a local agent classifies each job-alert email, extracts the postings it can verify, and merges them into the same feed. The mail never leaves your Mac.
  5. 5.You apply — every posting links out to the original source. Set a status, add a note, move on.

No accounts, no cloud, no telemetry. Your statuses and notes never sync anywhere.

Architecture

Two processes, one typed contract between them.

Job boards don't send CORS headers, and some reject non-browser clients outright — so unlike a web app, nothing is fetched from the UI. Every network call, parse, and write happens in the Electron main process; the renderer is a pure read/act client over a hand-typed bridge. That one inversion is what makes a strict connect-src 'self' policy free rather than aspirational.

Renderer

React 19 · read & act, never fetch

TanStack Query is the single source of truth for all UI state — no Redux, no Zustand, no context stores. Writes go through named mutations with optimistic patches and rollback; the local database is the cache, so job rows are never dehydrated to localStorage.

Main process

Fetch · validate · normalize · dedupe · store

A scheduler drives a sequential sync engine over seven provider plugins — one file each, with its own politeness budget declared in code rather than prose. Every response is validated at the boundary, so a board silently renaming a field is a failing test, not a 3 a.m. crash. One provider failing records its error and the other six still land.

Sequential + rate-limited zod at every boundary Cross-source dedupe PGlite — Postgres in WASM Drizzle migrations llama.cpp on-device

PGlite deliberately replaces a native SQLite binding: no ABI to rebuild against each Electron release, and the test suite runs the very same engine in memory — so repositories are tested against real Postgres, not a mock.

Engineering

The boundaries are compiler-enforced, not documented.

Twelve modules sit in five layers, and an illegal import is a lint error that fails the build — not a convention someone eventually violates. UI and data can never import each other; feature modules can never import each other; only the app layer composes them.

725 tests across 99 files, with an 85% coverage floor and 90% required on every changed line in CI.
3 TypeScript projects — main, renderer, and shared — with isolatedDeclarations forcing an explicit type on every export.
7 source plugins behind one contract. Adding a board touches one file, one fixture, one test — nothing else.
0 runtime dependencies fetched by the UI, and no telemetry anywhere. The strict CSP costs nothing because there is nothing to allow.
100% of provider tests run against captured live responses, so schema drift on a real board fails locally before it ever ships.
1 command to install, and a release pipeline that builds the dmg and bumps the Homebrew cask with no manual steps.

Install

Up and running in one command

# install

brew install --cask souhaibbenfarhat/tap/easyapply

# upgrade

brew upgrade --cask easyapply

# uninstall

brew uninstall --cask easyapply

# installed manually from the dmg instead? clear Gatekeeper's

# quarantine flag once, so the app opens without a "damaged" warning

xattr -dr com.apple.quarantine /Applications/EasyApply.app

EasyApply isn't notarized by Apple (it's ad-hoc signed) — the Homebrew cask clears the quarantine flag for you on install, so the xattr line is only needed if you download the dmg from GitHub Releases yourself. Either way, you can always audit the source.
